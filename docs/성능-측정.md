# 성능 측정 (perf 브랜치)

발표 전날 "실제 사이트가 램 8GB·내장 그래픽 노트북에서 실행부터 버벅이고 램이 꽉 찬다"는 문제를 재고 줄인 기록.
main은 우선 v3-polish 상태로 되돌려 두었다(되돌리기 커밋 b76d519, 히스토리는 그대로).

## 어떻게 쟀나

- 같은 PC(이 작업 PC, 외장 그래픽), Claude 앱 안 브라우저 창 1366×768, 화면 배율(devicePixelRatio) 1, 정문 출발 위치, 따라가기 카메라.
- 세 버전(v3-polish, realism 마지막 커밋 9a0d184, v5-detail)은 `git archive`로 따로 꺼내 같은 서버에서 **한 번에 하나만** 띄워 쟀다. 매번 가벼운 빈 페이지를 거친 뒤 불러왔다(앞 게임의 정리 시간이 섞이지 않게).
- 로딩 시간 = 페이지 요청 시작 → 첫 화면 준비(게임이 기록한 시각). 창이 가려져 타이머가 늦어져도 영향 없게 게임 안에서 기록.
- 페이지 안 측정: `performance.memory`(JS 힙), `renderer.info`(지오메트리·텍스처 수, 삼각형, 그리기 호출), 장면 안 텍스처·정점 버퍼 크기를 더해 GPU 메모리 추정, 원본 캔버스가 램에 남은 양, 그림자 맵, 화면 버퍼(MSAA 4배).
- 프로세스 측정: 빈 페이지일 때와 게임을 띄운 뒤의 브라우저 렌더러 프로세스 개인 메모리 차이(윈도 작업 관리자 값과 같은 종류). 4초 뒤(최고점 근처)와 14초 뒤(가라앉은 뒤).
- 한계: 이 PC는 외장 그래픽이라 GPU 메모리가 시스템 램에 잡히지 않는다. **내장 그래픽 노트북에서는 아래 "GPU 추정"만큼이 램을 더 쓴다.** 사용자의 노트북에서 직접 잰 값은 아니다(게임서버켜기.bat로 확인 필요).

| 나무 다양화·학생·노면 표시 | 삼각형 약 10만 | 넓은 활엽수·관목 줄기, 학생 40명(둥근 몸), 횡단보도·화살표 |
| 정점 배열 램 사본 | 21MB → 38MB | three.js는 GPU에 올린 뒤에도 자바스크립트 배열을 그대로 둠 → 내장 그래픽에선 같은 데이터가 램에 두 번 |

| 페이지 정리 | 약 7.9초 | v5 페이지를 떠날 때(새로 고침) 정리하는 데 걸린 시간 — 메모리를 많이 잡고 있다는 신호 |

## 최적화 (perf 브랜치)

| 바꾼 것 | 효과 |
|---|---|
| 첫 실행은 무조건 품질 "낮음" | 바닥 2048px, 그림자 없음, 화면 배율 1, 나무 절반, 가로등 숨김 |
| 화면 배율 상한 1.5 → 1.25 (높음) | 배율 1.5 노트북에서 화면 버퍼 약 72MB → 50MB |
| 그림자 맵 2048 → 1024 | 32MB → 8MB |
| 바닥 그림: GPU에 올린 뒤 원본 캔버스 해제, 높음 4096 → 3072px | 램 55MB → 0, GPU 76MB → 43MB(높음) |
| 바뀌지 않는 메시의 정점 배열을 GPU에 올린 뒤 해제 (`freeAfterUpload`) | 정점 배열 램 사본 38MB → 1.6MB |
| 차도 메시 간격 2.5m → 5m(꺾이는 곳 1m → 2.5m), 이음판 1.5m → 3m | 차도 지면을 이미 부드럽게 고쳐서 화면 차이 거의 없음, 삼각형 크게 줄어듦 |
| 먼 산 150m → 300m 격자, 따로 작은 파일(27KB) | 삼각형 8만 → 2만, 데이터 0.6MB → 27KB |
| 둘레 건물·주차 차량·셔틀버스·학생은 **기본 꺼짐**, 왼쪽 위 "바깥 건물"·"사람·차" 버튼으로 켤 때 그때 불러와 만듦 | 시작 메모리·로딩에서 빠짐. 끄면 숨기고 주차 차량 충돌도 뺌 |
| 켰을 때도 줄임: 주차 칸 60% → 35%(343대), 학생 40 → 24명(낮음 10명), 차·학생 모양 단순화 | 켜도 목표 안 |
| 교수님 캐릭터는 첫 화면이 뜬 1.5초 뒤(또는 지각 모드 시작 때) 만듦 | 로딩 0.6초 줄임 |

유지한 것: 지형(수치지도 + 차도 단차 정리), 건물 외관, 기념물, 노면 표시, 나무 종류, 시간 초과 연출, 조명·하늘. 지형 격자는 5m 그대로(정점 버퍼 7MB, 램 사본은 해제) — 줄이면 옹벽·단차가 뭉개져서 두었다.
